# Тестирование объявлений (Тестовое задание Avito QA)

Решение тестового задания на позицию стажёра QA от Avito, осенняя волна 2026.

- **Исходное задание:** https://github.com/avito-tech/tech-internship/blob/main/Tech%20Internships/QA/QA-trainee-assignment-autumn-2026/QA-trainee-assignment-autumn-2026.md

## Описание задачи

Задание состоит из двух обязательных частей: поиска багов по скриншотам и тестирования сервиса. Для второй части выбран вариант 2.1 (API).

**Задание 1. Поиск багов по скриншотам:**

- Сравнить форму редактирования объявления, карточку продавца и карточку товара.
- Найти и описать ошибки. Значения в форме редактирования считать эталоном ожидаемого результата.
- Назначить приоритет каждому багу: P0 - критический, P1 - высокий, P2 - средний, P3 - низкий.

**Задание 2.1. Тестирование API:**

Дан микросервис для работы с пользователями, объявлениями и статистикой. Необходимо составить тест-кейсы, автоматизировать их и проверить результаты.

**Доступные запросы:**

- `POST /api/1/register` - регистрация пользователя.
- `POST /api/1/autorize` - авторизация и получение bearer-токена.
- `POST /api/1/item` - создание объявления.
- `GET /api/1/item/{id}` - получение объявления по идентификатору.
- `GET /api/1/{sellerID}/item` - получение объявлений продавца.
- `GET /api/1/statistic/{id}` - получение статистики объявления, версия 1.
- `GET /api/2/statistic/{id}` - получение статистики объявления, версия 2.
- `DELETE /api/2/item/{id}` - удаление объявления.

**Требования к проверкам:**

- Покрыть позитивные и негативные сценарии, граничные значения и корнер-кейсы.
- Проверить регистрацию, авторизацию и доступ к защищённым запросам.
- Добавить содержательные проверки через `assert`.
- Создавать пользователей и тестовые данные динамически. При создании объявления использовать `sellerID` пользователя, которому принадлежит токен.
- Обеспечить независимость тестов от порядка запуска и данных других участников общего стенда.
- После проверок по возможности удалять созданные объявления.
- Оформить тест-кейсы, инструкцию запуска и найденные дефекты.

**Тестовый стенд:** https://qa-internship.avito.com

## Как запустить тесты

Потребуются Python 3.10 или новее и доступ к `https://qa-internship.avito.com`. Откройте терминал в корневой папке проекта и используйте команды для своей системы.

### macOS и Linux

1. Откройте терминал в корневой папке проекта.
2. Создайте и активируйте виртуальное окружение:

   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   ```

3. Установите зависимости:

   ```bash
   python -m pip install -r requirements.txt
   ```

4. Запустите весь набор с сохранением отчёта:

   ```bash
   python -m pytest -q --reruns 3 --reruns-delay 2 \
     --only-rerun "Нет ответа стенда" \
     --only-rerun "сетевая ошибка очистки" \
     --junitxml=results.xml
   ```

Эта команда повторяет только тесты, прерванные сетевыми ошибками, не более трёх раз с паузой 2 секунды. Сам HTTP-клиент автоматически не отправляет повторный POST; повторяется тест целиком. Падения проверок содержимого и кодов ответов API не повторяются по этому правилу. Для запуска без повторов используйте `python -m pytest -q --junitxml=results.xml`.

Запуск в обратном порядке:

```bash
python -m pytest -q --reverse --junitxml=results_reverse.xml
```

Запуск одного API-теста:

```bash
python -m pytest -q test_api.py::test_register_new_user
```

Только локальные проверки, без доступа к стенду:

```bash
python -m pytest -q test_client_unit.py
```

### Windows (PowerShell)

1. Создайте виртуальное окружение:

   ```powershell
   py -3 -m venv .venv
   ```

   Если команда `py` недоступна, используйте `python -m venv .venv`.

2. Установите зависимости:

   ```powershell
   .\.venv\Scripts\python.exe -m pip install -r requirements.txt
   ```

3. Запустите весь набор с сохранением отчёта. Команда вводится одной строкой:

   ```powershell
   .\.venv\Scripts\python.exe -m pytest -q --reruns 3 --reruns-delay 2 --only-rerun "Нет ответа стенда" --only-rerun "сетевая ошибка очистки" --junitxml=results.xml
   ```

Для Windows активация окружения не требуется: команды напрямую вызывают Python из `.venv`. Поэтому не нужно менять политику выполнения PowerShell или запускать `Activate.ps1`.

Запуск без сетевых повторов:

```powershell
.\.venv\Scripts\python.exe -m pytest -q --junitxml=results.xml
```

Запуск в обратном порядке:

```powershell
.\.venv\Scripts\python.exe -m pytest -q --reverse --junitxml=results_reverse.xml
```

Запуск одного API-теста:

```powershell
.\.venv\Scripts\python.exe -m pytest -q test_api.py::test_register_new_user
```

Только локальные проверки, без доступа к стенду:

```powershell
.\.venv\Scripts\python.exe -m pytest -q test_client_unit.py
```

Тесты используют уникальные имена и собственные объявления. Существующие данные других участников не используются. Удаление пользователей и отдельное удаление статистики коллекцией не предусмотрены.

## Как проверялось

Скриншоты сравнивались по полям с формой редактирования. Для каждого расхождения указаны место, фактический и ожидаемый результат, а также приоритет.

API-набор запускался на общем стенде Avito. Проверенное окружение: Python 3.14.4, pytest 9.2.0, requests 2.34.2.

После полного набора отдельно запущен `test_register_new_user`: `1 passed in 1.21s`. Тест самостоятельно подготовил новые данные.

**Полный прогон текущей версии: `55 passed, 2 failed in 128.50s`.** Всего 57 проверок: 51 API и 6 модульных. Этот запуск выполнен после исправления данных BOUND-01, ITEM-03 и ITEM-04, с выборочным повторением только сетевых ошибок (не более трёх повторов на тест). Проверки результатов API не ослаблялись; падения API-01/02 под правило сетевых повторов не попадают. В этом запуске потребовался один сетевой повтор (1 rerun), после которого проверка прошла. Два падения соответствуют API-01 и API-02. Других итоговых падений и ошибок подготовки нет.

**Повторная проверка после исправления данных: `6 passed in 11.33s`.** Проверены базовое создание и чтение, три цены (-1, 0, 1), чужой sellerID и заголовок X-UserId. Во всех этих сценариях используется корректная статистика из коллекции: likes = 21, viewCount = 11, contacts = 43. Ранее нулевые счётчики могли приводить к отказу независимо от проверяемой цены или владельца.

На стенде получены ответы: цена -1 - HTTP 200 с сохранением переданного значения; 0 - HTTP 400 без создания объявления; 1 - HTTP 200 с сохранением переданного значения. Это наблюдаемое поведение, а не опубликованное правило допустимого диапазона. Первый повторный запуск не дошёл до сценариев из-за HTTPS-соединения; указанный успешный результат относится к следующему запуску.

**Обратный порядок текущей версии: `55 passed, 2 failed in 68.56s`.** Два падения соответствуют API-01 и API-02. Других итоговых падений и ошибок подготовки нет. Используется тот же исправленный код и то же время ожидания: соединение 10 секунд, чтение 45 секунд. В обратном прогоне сетевые повторы не включались.

Каждый дефект статистики дополнительно воспроизведён на новом объявлении: удаление вернуло 200, чтение объявления - 404, а статистика сохранила прежние значения. Пока дефекты не исправлены на стороне сервиса, два соответствующих теста должны падать; это отражается в отчёте и коде завершения pytest.

Границы цены -1/0/1 и счётчиков 0/1 проверяются на согласованность принятия или отклонения данных: неопубликованные минимумы не выдумываются. Это не заменяет проверку точных диапазонов после получения спецификации.
