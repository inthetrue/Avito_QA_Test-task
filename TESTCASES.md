# Тест-кейсы API

Источник: [Postman-коллекция Avito](postman_collection.json) и [условие задания](https://github.com/avito-tech/tech-internship/blob/main/Tech%20Internships/QA/QA-trainee-assignment-autumn-2026/QA-trainee-assignment-autumn-2026.md).

Документ описывает план проверок: предусловия, шаги и ожидаемые результаты. Для неуказанных в источнике правил отдельно отмечены вопросы к требованиям.

## Общие предусловия

- Стенд: `https://qa-internship.avito.com`.
- Для запросов с телом используется `Content-Type: application/json`.
- Пользователи создаются заново для каждого независимого теста. Имя содержит случайный суффикс, корректный пароль для базовых сценариев - `strong-password`, как в примере коллекции.
- Пользователь A, его токен и объявление A в таблицах означают данные, созданные в предусловиях именно этого теста.
- Защищённые запросы получают заголовок `Authorization: Bearer <accessToken>`, кроме тестов отсутствующего или неверного токена.
- `sellerID` берётся из `id` ответа регистрации; токен получается авторизацией того же пользователя.
- Исходные данные объявления: `name = testItem_<суффикс>`, `price = 9900`, `statistics = {"likes": 21, "viewCount": 11, "contacts": 43}`. Это примеры допустимых данных из коллекции, а не границы допустимых значений.
- UUID объявления извлекается из строки `status` ответа создания. Нельзя ожидать отдельное поле `id` в этом ответе.
- После каждой проверки необходимо удалять созданные объявления собственным токеном. При проверке повторного удаления следует различать первое удаление (ожидается 200) и повторное (ожидается 404). Удаление пользователей в коллекции не предусмотрено.
- Подготовка данных через другие ручки - предусловие отдельного теста, а не отдельный дополнительный E2E-тест.

## 1. Регистрация

Техника: классы эквивалентности для корректных, пустых и отсутствующих учётных данных.

| ID | Предусловия | Шаги | Ожидаемый результат |
|---|---|---|---|
| REG-01 | Уникальный username, password = strong-password | POST `/api/1/register` с этими данными, без токена | 201; JSON содержит целочисленный id и переданный username; пароль в ответе отсутствует |
| REG-02 | Уже зарегистрирован A | Повторить регистрацию с тем же username и password, не меняя username | 409; новый пользователь не создаётся |
| REG-03 | Уникальный username | Отправить регистрацию без поля password | 400; успешной регистрации нет |
| REG-04 | Password = strong-password | Отправить регистрацию без поля username | 400; успешной регистрации нет |
| REG-05 | Password = strong-password | Отправить username равный пустой строке | 400; успешной регистрации нет |
| REG-06 | Уникальный username | Отправить password равный пустой строке | 400; успешной регистрации нет |
| REG-07 | Нет | Отправить синтаксически неверный JSON | 400; обработанная ошибка, без 5xx |
| REG-08 | Для остальных полей используются базовые данные | По отдельности передать null и число вместо username и password | 400; успешной регистрации нет |

В Postman перед регистрацией автоматически генерируется новый username. Для REG-02 этот скрипт нужно отключить либо отправить отдельный запрос с фиксированным именем A, иначе получится регистрация другого пользователя.

## 2. Авторизация

Техника: классы эквивалентности для верных и неверных учётных данных.

| ID | Предусловия | Шаги | Ожидаемый результат |
|---|---|---|---|
| AUTH-01 | Зарегистрирован A | POST `/api/1/autorize` с его username и password, без токена | 200; непустой accessToken; tokenType равен Bearer |
| AUTH-02 | Зарегистрирован A с password = strong-password | Передать его username и password = wrong-password | 401; токен не выдан |
| AUTH-03 | Уникальное незарегистрированное имя | Авторизоваться с этим именем и password = strong-password | 401; токен не выдан |
| AUTH-04 | Зарегистрирован A | Отправить запрос без поля password | 400; токен не выдан |
| AUTH-05 | Нет | Отправить синтаксически неверный JSON | 400; обработанная ошибка, без 5xx |
| AUTH-06 | Зарегистрирован A | Отправить запрос без поля username | 400; токен не выдан |

## 3. Создание объявления

Техника: позитивный сценарий, проверка принадлежности данных и корнер-кейс одинаковых объявлений.

| ID | Предусловия | Шаги | Ожидаемый результат |
|---|---|---|---|
| ITEM-01 | A авторизован | POST `/api/1/item` с базовыми данными и sellerID A | 200; JSON содержит status с корректным UUID; GET по UUID возвращает созданные name, price и sellerId/sellerID согласно схеме ответа |
| ITEM-02 | A авторизован | Дважды создать объявления с одинаковыми name, price, sellerID и statistics | Оба ответа 200; UUID различаются; обе записи находятся в списке A |
| ITEM-03 | Созданы и авторизованы A и B | Создать объявление с токеном A, но sellerID B | Запрос отклонён, UUID не выдан; в списке B новая запись отсутствует. Точный код для этой ситуации нужно уточнить: описание ручки перечисляет 400 и 401, но не связывает код с причиной |
| ITEM-04 | Созданы A и B; A авторизован, id B сохранён | Создать объявление с базовым телом A, но X-UserId равным id B | Заголовок не меняет владельца: объявление не может быть записано на B. Допустимо игнорирование заголовка или явный отказ; обязательный вариант контрактом не указан |
| ITEM-05 | A авторизован | Отправить синтаксически неверный JSON | 400; объявление не создано, 5xx отсутствует |

## 4. Получение объявления

Техника: классы эквивалентности идентификатора - существующий, отсутствующий и некорректный.

| ID | Предусловия | Шаги | Ожидаемый результат |
|---|---|---|---|
| GET-01 | A авторизован, создано объявление A | GET `/api/1/item/{id}` с его UUID | 200; массив из одного объявления; UUID и доступные поля соответствуют созданной записи |
| GET-02 | A авторизован; его объявление создано и успешно удалено | GET по UUID удалённого объявления | 404; удалённая запись не возвращается как существующая |
| GET-03 | A авторизован | GET `/api/1/item/not-a-uuid` | 400; обработанная ошибка, без 5xx |

## 5. Объявления продавца

Техника: границы количества записей 0, 1 и 2.

| ID | Предусловия | Шаги | Ожидаемый результат |
|---|---|---|---|
| LIST-01 | Новый A авторизован, объявлений нет | GET `/api/1/{sellerID}/item` с id A | 200; пустой массив |
| LIST-02 | У нового A создано одно объявление | Получить список A | 200; массив содержит ровно созданную запись с её UUID |
| LIST-03 | У нового A созданы два объявления | Получить список A | 200; массив содержит оба созданных UUID; порядок записей не фиксируется |
| LIST-04 | У A созданы два объявления | Удалить одно; получить список A | 200; оставшееся объявление есть, удалённого UUID нет |

## 6. Статистика v1

| ID | Предусловия | Шаги | Ожидаемый результат |
|---|---|---|---|
| STAT1-01 | A авторизован, создано объявление A с базовыми счётчиками | GET `/api/1/statistic/{id}` с UUID A | 200; массив из одного объекта со счётчиками likes, viewCount и contacts; значения числовые и неотрицательные |
| STAT1-02 | A авторизован; его объявление создано и удалено; GET объявления возвращает 404 | Получить статистику v1 по удалённому UUID | 404; прежние счётчики не возвращаются. |
| STAT1-03 | A авторизован | GET `/api/1/statistic/not-a-uuid` | 400; обработанная ошибка, без 5xx |

## 7. Статистика v2

| ID | Предусловия | Шаги | Ожидаемый результат |
|---|---|---|---|
| STAT2-01 | A авторизован, создано объявление A с базовыми счётчиками | GET `/api/2/statistic/{id}` с UUID A | 200; JSON-объект или массив из одного объекта со счётчиками likes, viewCount и contacts; значения числовые и неотрицательные. Точное равенство схем v1/v2 не предполагается |
| STAT2-02 | A авторизован; его объявление создано и удалено; GET объявления возвращает 404 | Получить статистику v2 по удалённому UUID | 404; прежние счётчики не возвращаются. |

В описании v2 также перечислен код 100 без сценария его применения. Его нельзя автоматически считать критерием успешного получения статистики. Требуется уточнение контракта.

## Граничные значения

| ID | Предусловия | Шаги | Ожидаемый результат |
|---|---|---|---|
| BOUND-01 | Новый A авторизован; все остальные поля корректны, statistics = {likes: 21, viewCount: 11, contacts: 43} из коллекции | Создать объявление отдельно с price = -1, 0 и 1; менять только price, сохраняя остальные данные корректными | Должен быть контролируемый ответ 400 либо успешный 200. Если значение принято, при чтении должна сохраняться точная переданная цена; если отклонено, записи нет. Это проверка согласованности валидации вокруг нуля; допустимый минимум цены в условии не задан |
| BOUND-02 | Новый A авторизован | Создать объявление отдельно со всеми счётчиками равными 0 и равными 1 | Контролируемый 400 без создания записи либо 200 с доступным для чтения объявлением. Проверка точных минимальных значений требует контракта |

Ещё одна граница проверяется в LIST-01..03: пустой список, одна и две записи. Для полного анализа максимальной длины и максимальной цены нужны ограничения поставщика API. Принимать оба кода в BOUND-01/02 можно только для исследования неопубликованной политики; в сценариях с известным контрактом коды проверяются строго.

## 8. Удаление объявления

| ID | Предусловия | Шаги | Ожидаемый результат |
|---|---|---|---|
| DEL-01 | A авторизован, создано объявление A | DELETE `/api/2/item/{id}`; затем GET по тому же UUID | DELETE возвращает 200; последующий GET возвращает 404 |
| DEL-02 | A авторизован; его объявление создано и успешно удалено | Повторить DELETE по тому же UUID | 404; обработанная ошибка, без 5xx |
| DEL-03 | A авторизован | DELETE `/api/2/item/not-a-uuid` | 400; обработанная ошибка, без 5xx |

## 9. Доступ к защищённым запросам

Каждая строка ниже выполняется отдельно для каждого из шести защищённых запросов: создания объявления, чтения объявления, списка продавца, статистики v1, статистики v2 и удаления. Получается 12 самостоятельных проверок.

Предусловия: в каждом тесте A зарегистрирован, его объявление создано с корректным токеном. URL, sellerID и тело запроса валидны; меняется только заголовок авторизации.

| ID | Шаги | Ожидаемый результат |
|---|---|---|
| ACCESS-01 | Отправить защищённый запрос без Authorization | 401; защищённые данные не выдаются, объявление не создаётся и не удаляется |
| ACCESS-02 | Отправить защищённый запрос с Authorization: Bearer invalid-token | 401; защищённые данные не выдаются, объявление не создаётся и не удаляется |

Для создания и удаления дополнительно проверить отсутствие изменений корректным токеном A через список продавца или получение объявления.

## 10. Воспроизводимость

Эти сценарии предназначены для этапа проверки будущего набора автотестов.

| ID | Предусловия | Шаги | Ожидаемый результат |
|---|---|---|---|
| RUN-01 | Реализован набор автотестов | Запустить полный набор, затем отдельный тест | Результат отдельного теста не зависит от предыдущего запуска; данные создаются заново |
| RUN-02 | Реализован набор автотестов | Запустить тесты в обратном порядке | Предусловия не берутся из соседних тестов; все созданные объявления очищаются, кроме удаляемых самим сценарием |

## Что требуется уточнить для завершения тест-дизайна

Коллекция содержит примеры, но не полную спецификацию валидации. Ниже - запланированные проверки, для которых пока нельзя назначить точный ожидаемый результат.

| Область | Что выяснить | Какие проверки добавить |
|---|---|---|
| Username и password | Минимальную и максимальную длину, допустимые символы, обработку пробелов, null и неверных типов | min-1, min, min+1; max-1, max, max+1; null, числа и пробельные строки |
| Name объявления | Обязательность, длину, допустимость пустой строки и null | Пустое/отсутствующее значение, границы длины, неверные типы |
| Price | Минимум, максимум, дробность и допустимость нуля | 0 и отрицательное значение, значения на границах и за ними, дробное и неверный тип; ожидания после уточнения правил |
| Statistics | Обязательность полей, диапазоны счётчиков и полная схема ответа каждой версии | Отсутствующие и неверные значения, точные границы счётчиков после получения спецификации |
| Доступ между пользователями | Кто вправе читать и удалять чужое объявление, какой код отказа задан | Проверки с токенами A и B для каждой ручки с однозначным ожидаемым результатом |
| Дефекты и ошибки | Формат тела ошибки, Content-Type для ошибок и точные коды спорных сценариев | Проверки схем ошибок; варианты ITEM-03, ITEM-04 и некорректный UUID для статистики v2 |

Эти уточнения не заменяют тесты граничных значений из условия. После установления правил нужно дополнить случаи и только затем считать покрытие завершённым.
